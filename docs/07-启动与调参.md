# 07 · 启动与调参

这一章给出**可以直接抄**的启动命令，并解释每一个参数存在的理由。
所有命令都在仓库根目录执行。

生产配置是：**层切分 ×3 + LiLiCorr(DFlash) 草稿 + 1M 上下文**，实测 decode 54–55 tok/s。
TP 配置作为回退保留（46.6–47.7 tok/s）。

---

## 1. 启动前检查

```bash
# 1) 三张卡都在、显存干净
nvidia-smi --query-gpu=index,name,memory.used,memory.total --format=csv

# 2) 三个模型文件在
ls -lh model/bolt74b/*-IQ2_XXS.gguf
ls -lh model/draft/*.gguf
ls -lh model/mmproj-BF16.gguf

# 3) 校验（可选，几分钟）
bash scripts/verify-model.sh --all

# 4) NCCL 能被找到
export NCCL_DIR=${NCCL_DIR:-$HOME/nccl-venv/lib/python3.12/site-packages/nvidia/nccl}
ls "$NCCL_DIR/lib/libnccl.so.2"

# 5) 二进制在
ls llama.cpp/build-nccl/bin/llama-server
```

如果 `memory.used` 不是接近 0，先结束上次残留的 `llama-server`：

```bash
pkill -f llama-server
nvidia-smi          # 等显存释放，通常 2–5 秒
```

## 2. 生产配置：层切分 + LiLiCorr 草稿 + 1M

### 2.1 用脚本（推荐）

```bash
bash scripts/run-draft.sh                 # 前台，Ctrl-C 停止
bash scripts/run-draft.sh --daemon        # 后台 + 等待 /health（冷缓存最多 40 分钟）
bash scripts/run-draft.sh --status
bash scripts/run-draft.sh --stop
```

脚本默认值就是生产配置，不需要额外环境变量。常用覆盖：

```bash
SM=tensor bash scripts/run-draft.sh            # TP + 草稿（更慢，见 docs/12）
NMAX=3 bash scripts/run-draft.sh               # 1M 下更保守的草稿长度
CTX=204800 CTK=q8_0 CTV=q8_0 NMAX=3 \
  bash scripts/run-draft.sh                    # 200K + 高质量 KV
SPEC=none bash scripts/run-draft.sh            # 临时关闭草稿做对照
```

### 2.2 手写命令（等价）

```bash
export LD_LIBRARY_PATH="$NCCL_DIR/lib:$PWD/llama.cpp/build-nccl/bin:$LD_LIBRARY_PATH"

./llama.cpp/build-nccl/bin/llama-server \
  -m model/bolt74b/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-IQ2_XXS.gguf \
  -ngl all -sm layer -ts 1,1,1 -fa on \
  -ctk q4_0 -ctv q4_0 -c 1048576 -ub 64 \
  -t 17 -np 1 -fit off \
  -md model/draft/dflash-NVIDIA-Nemotron-3.5-Bolt-74B-A9B-NVFP4.gguf \
  -ngld all --spec-type draft-dflash \
  --spec-draft-n-max 4 --spec-draft-n-min 0 \
  -mm model/mmproj-BF16.gguf --no-mmproj-offload \
  --override-kv nemotron_h_moe.context_length=int:1048576 \
  --metrics --host 127.0.0.1 --port 8080 -lv 3
```

启动成功的日志特征：

```
llama_model_load: model size  = ... MiB
llama_kv_cache: ... size = ... MiB (per device)
main: server is listening on http://127.0.0.1:8080
```

（`model size` 与 KV 的具体数值随分配策略变化，看日志里的数字最准。）

显存方面：层切分下三卡的权重分布不再需要镜像 KV，草稿本身只有约 0.93 GiB
（整份放在一张卡上，或按 `-ngld all` 分布到各卡）。用 `nvidia-smi` 确认每卡
都留有至少 0.3–0.5 GB 余量；如果某张卡贴到 12 GB，先把 `-ub` 降到 64 或把
`CTX` 降到 200K。

## 3. 每个参数为什么在这里

| 参数 | 作用 | 不写会怎样 |
|---|---|---|
| `-m <file>` | 主模型路径 | 必填 |
| `-ngl all` | 所有层放 GPU | 部分层留在 CPU，慢 3–10 倍 |
| `-sm layer` | **层切分**（生产）：每张卡拿连续的若干层 | 默认就是 layer；但显式写便于排查 |
| `-ts 1,1,1` | 三卡等分 | 三张 3060 相同，等分即可 |
| `-fa on` | FlashAttention | 长上下文显存暴涨，1M 直接 OOM |
| `-ctk q4_0 -ctv q4_0` | KV cache 量化到 4 bit | 1M 下 KV 总量约 2.25 GiB，层切分后约 0.75 GiB/卡；q8_0 会把这块翻倍 |
| `-c 1048576` | 上下文 1M | 默认 4096，长文被截断 |
| `-ub 64` | 物理批大小 | 1M 下 128/256 会 OOM（草稿让验证批次更宽） |
| `--override-kv ...context_length=int:1048576` | 绕过模型元数据里的 262144 上限 | llama.cpp 会把 `-c` 钳到 262144 |
| `-t 17` | CPU 线程（留 1–2 核给系统） | 默认全核，可能和 CUDA 线程抢核 |
| `-np 1` | 单并发槽 | 默认 1；改大会按槽位复制 KV 与 SSM 状态 |
| `-fit off` | 关闭显存自动拟合 | 启动时会加载两遍模型"试装"，白等 5–10 分钟 |
| **`-md <draft>`** | **草稿模型路径** | 不开草稿，回到 40 tok/s（层切分） |
| **`-ngld all`** | 草稿也放 GPU | 草稿放 CPU 实测只有 21.9 tok/s |
| **`--spec-type draft-dflash`** | 用 NVIDIA DFlash 协议做投机解码 | 只给 `-md` 不给类型，不会启用 |
| **`--spec-draft-n-max 4`** | 每步最多起草 4 个 token | 默认值不同；4 是 1M 下的最优（见 §4） |
| **`--spec-draft-n-min 0`** | 至少起草 0 个 | 允许草稿"放弃"，短回复不浪费 |
| `-mm <mmproj>` | 视觉投影器 | 不能处理图片 |
| `--no-mmproj-offload` | 视觉编码器放 CPU | 编码器占约 1.6 GB 显存，三卡都紧 |
| `--metrics` | 暴露 `/metrics` | 无法用 Prometheus/脚本读 tok/s 与接受率 |
| `--host 127.0.0.1` | 只监听本机 | 默认 0.0.0.0，局域网可访问（有风险，见 08） |
| `-lv 3` | 详细日志 | 出问题时看不到切分/加载细节 |

### 3.1 `-fit off` 到底省了什么

llama.cpp 新版本默认会先加载一遍模型估算每层显存，再调整 `-ngl`/`-ts`。
22 GB 模型在 USB2 盘上加载一遍要 8 分钟，两遍就是 16 分钟。
这里所有参数都手工算好，不需要它拟合。

> 如果你改了卡数或模型，不确定能不能装下，可以先**去掉** `-fit off` 让它自动试一次，
> 记下它算出的结果，再手工固定参数。

### 3.2 为什么 KV 是 q4_0

1M 上下文下 KV 公式（**全部注意力层的总量**）：

```
2 × 8 层 × 2 头 × 128 × 1,048,576 × 0.5 B(q4_0) ≈ 2.25 GiB
```

- **层切分**：按层分布到三张卡，平均每卡约 **0.75 GiB**（不均匀，看哪张卡分到几层）；
- **张量并行**：2 个 KV 头 < 3 张卡，每卡**镜像一份**，即每卡 **2.25 GiB**。

换成 q8_0 总量是 4.3 GiB：层切分约 1.43 GiB/卡，TP 则每卡 4.3 GiB 直接装不下。
1M 生产配置选 q4_0，是为了在层切分下给草稿和 compute buffer 再留出余量。

200K/400K 上下文则相反：q8_0 总量只有 850 MiB / 1.7 GiB，按层分布后每卡更小，精度更高，优先 q8_0。

## 4. 草稿长度 `n_max` 怎么选

`--spec-draft-n-max` 是"每步最多猜几个 token"。它**不是越大越好**：
猜得越多，验证批次越大，单步越慢；而且后面几个猜测的接受率会下降。

本机实测（greedy，接受长度指平均被接受的草稿 token 数）：

| 上下文 | KV | `n_max` | decode | 接受长度 |
|---:|---|---:|---:|---:|
| **1M** | q4_0 | **4** | **54.0–55.0** | **3.42** |
| 1M | q4_0 | 3 | 48.5–50.6 | 2.70 |
| 200K | q8_0 | 3 | 55.5 | 2.92 |
| 400K | q8_0 | 3 | 55.2 | 2.92 |
| 32K（TP） | q8_0 | 4 | 45.1 | 2.83 |
| 1M（草稿放 CPU） | q4_0 | 4 | 21.9 | 2.90 |

结论：

- **1M 用 `n_max=4`**。KV 已经很大，把 `n_max` 提到 5 只会让验证位置从 5 增到 6，额外显存/时间不划算；
- **200K/400K 用 `n_max=3`**，配 q8_0 KV，略快于 1M 配置；
- 温度 0.7 时接受率下降，实测 49–52 tok/s，属正常现象；
- 如果你的任务高度重复（代码补全、模板填充），接受长度会更高；自由创作则更低。

机制与公式见 [12-草稿模型与投机解码](12-草稿模型与投机解码.md)。

## 5. 其它可用配置

### 5.1 回退：TP×3 + 1M（无草稿）

```bash
bash scripts/run-tp.sh --daemon
```

等价命令：

```bash
export LD_LIBRARY_PATH="$NCCL_DIR/lib:$PWD/llama.cpp/build-nccl/bin:$LD_LIBRARY_PATH"
export LLAMA_SM_TENSOR_ALLOW_ARCH=1

./llama.cpp/build-nccl/bin/llama-server \
  -m model/bolt74b/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-IQ2_XXS.gguf \
  -ngl all -sm tensor -ts 1.02,1.02,0.96 -fa on \
  -ctk q4_0 -ctv q4_0 -c 1048576 -ub 64 \
  -t 17 -np 1 -fit off \
  -mm model/mmproj-BF16.gguf --no-mmproj-offload \
  --override-kv nemotron_h_moe.context_length=int:1048576 \
  --metrics --host 127.0.0.1 --port 8080 -lv 3
```

实测 46.6–47.7 tok/s。**预填充比生产配置快约 2 倍**，所以它是"长 prompt、短回复"
场景的合理回退。注意 `-ub` 必须是 64，1M + TP 的显存余量很小。

### 5.2 TP + 262K（不需要 1M 时最省事）

```bash
... -sm tensor -ts 1,1,1 -ctk q8_0 -ctv q8_0 -c 262144 -ub 256 ...
```

实测 46.8 tok/s，比 1M 配置还略快（KV 更小、mask 更小）。不需要 tpfit。

### 5.3 层切分 + 200K（无草稿、要最快预填充）

```bash
... -sm layer -ts 1,1,1 -ctk q8_0 -ctv q8_0 -c 204800 -ub 512 ...
```

decode 40.3 tok/s，prefill 1489 tok/s。三卡是流水线，同一时刻只有一张卡忙。

### 5.4 显存不够：把专家放内存

```bash
# 稠密权重进显存，专家按需从 RAM 换入
... -cmoe --moe-cache-mib 8192 ...

# 或把 N 层专家留在 CPU
... -ncmoe 8 ...
```

实测 35.7 / 35.0 tok/s。**`-cmoe` 与 `-sm tensor` 互斥**，只能配 `-sm layer`。

### 5.5 多并发

```bash
... -np 4 -c 262144 ...
```

- KV 缓存按槽位复制，`-np 4` 就是 4 份；
- 回退组（0001–0004）的 SSM 状态回写在 TP 路径断言 `K == 1`（每个 ubatch 只能有 1 个序列）。
  实测 TP + `-np 4` 聚合 **82.9 tok/s**，但高并发下多个序列被合进同一 ubatch
  会触发断言；生产组（0005）已放宽为按批次自适应；
- 需要稳定并发时优先层切分，或让请求在客户端排队。

复现 4 路聚合（回退配置）：

```bash
NP=4 CTX=16384 bash scripts/run-tp.sh
```

## 6. 上下文长度的取舍

生产（层切分 + 草稿）与回退（TP）的数字不同，分开看：

**生产：层切分 + 草稿**

下表 KV/卡按层切分、三卡平均估算（实际按层分布，单卡会有出入；总量见 [02](02-选型计算.md) §4.2）：

| 上下文 | KV 类型 | KV/卡（平均） | `-ub` | decode | prefill | 适用 |
|---:|---|---:|---:|---:|---:|---|
| 8K / 32K | q8_0 | ~12 / ~45 MiB | 128–256 | 未单独实测，应 ≥ 55 | 未单独实测 | 普通对话、长文档 |
| 200K | q8_0 | ~283 MiB | 64 | 55.5（n_max=3） | 约 460 tok/s（413 s） | 长文 + 高质量 KV |
| 400K | q8_0 | ~0.6 GiB | 64 | 55.2（n_max=3） | 未单独实测 | 超长文 |
| 1M | q4_0 | ~0.75 GiB | 64 | **54–55** | ≥ 30 分钟（约为回退的 2 倍） | 本项目生产 |

> **草稿的代价在预填充**：草稿要先把整个 prompt 也过一遍，所以长 prompt 的
> `prompt eval` 大约是回退配置的一半。19K prompt：1269 → 616 tok/s；
> 200K 约 413 s；1M 需要 30 分钟以上（回退约 17 分钟）。
> 短 prompt 不受影响，因为草稿只处理新来的那一段。

**回退：TP×3，无草稿**

| 上下文 | KV 类型 | KV/卡 | `-ub` 上限 | decode | 适用 |
|---:|---|---:|---:|---:|---|
| 8K | q8_0 | ~34 MiB | 512 | 46+ | 普通对话 |
| 32K | q8_0 | ~136 MiB | 512 | 46+ | 长文档 |
| 200K | q8_0 | ~850 MiB | 512 | 46.4 | 长文 + 高质量 KV |
| 262K（原生） | q8_0 | ~1.1 GiB | 256 | 46.8 | 原版 IQ2 上限 |
| 1M | q4_0 | ~2.25 GiB | 64 | 46.6–47.7 | 百万上下文 |

> 原生上限 262144 写在 GGUF 元数据里。超过它必须 `--override-kv`，
> 这是"模型没在这么长上训练过"的提示，不是硬错误——但**质量未验证**。

## 7. 启动慢/失败怎么定位

| 阶段 | 正常耗时 | 卡住时看什么 |
|---|---|---|
| 读 GGUF 头 | < 1 s | 文件是否在 USB2 盘/是否损坏 |
| 加载权重 | 3–8 min（USB2） | `-lv 3` 里的 `loading tensor` 进度 |
| 加载草稿 | 10–60 s | 是否 `unknown model architecture 'dflash'` |
| 分配 KV | 5–20 s | 是否 OOM，`nvidia-smi` 显存 |
| NCCL 初始化 | 2–10 s | 是否有 `libnccl.so.2` |
| 监听端口 | 立即 | 端口被占用？`ss -ltnp \| grep 8080` |

### 7.1 常见启动错误

| 报错 | 原因 | 处理 |
|---|---|---|
| `unknown model architecture 'dflash'` | 引擎不支持 LiLiCorr 草稿 | 用 `5aeac37` + 补丁 0005 编译 |
| `failed to allocate ... draft` / CUDA0 OOM | TP + 1M + 草稿显存不够 | 改 `-sm layer`；或 `-ub 64` |
| `arch not supported for tensor split` | 没设 `LLAMA_SM_TENSOR_ALLOW_ARCH=1` | 只在 `-sm tensor` 时需要 |
| `error while loading shared libraries: libnccl.so.2` | `LD_LIBRARY_PATH` 没含 NCCL | 见第 1 节 |
| `CUDA error: out of memory`（device 2） | `-ub` 太大 | 1M 下用 `-ub 64` |
| `failed to allocate ... KQ mask` | 1M + `-ub 256` | 降到 128 或 64 |
| `unknown model architecture 'nemotron_omni'` | 没打 0004 或 0005 所在的新引擎 | 去掉 `-mm` 或换引擎 |
| `tensor 'blk.1.ffn_gate_inp.weight' has wrong shape` | 回退组没打 0001 | 回到 04 |
| 图像描述全错但不报错 | 投影器不配对（393 张量） | 换 Bolt 仓库那份（519 张量） |
| `-cmoe` 抛异常 | 与 `-sm tensor` 同用 | 改 `-sm layer` |
| 启动成功但首 token 极慢 | 首次 CUDA kernel 编译/页缓存冷 | 预热一次即可 |

## 8. systemd 常驻

模板在 `systemd/` 下，三个单元：

| 单元 | 用途 |
|---|---|
| `bolt-serve.service` | 生产：层切分 + 草稿 + 1M |
| `bolt-serve-tp.service` | 回退：TP×3 + 1M，无草稿 |
| `bolt-strata-ui.service` | Trata 网页与 API 代理 |

安装（用户级，不需要 root）：

```bash
mkdir -p ~/.config/systemd/user
cp systemd/bolt-serve.service systemd/bolt-serve-tp.service \
   systemd/bolt-strata-ui.service ~/.config/systemd/user/
# 编辑里面的 WorkingDirectory / ExecStart / Environment
systemctl --user daemon-reload
systemctl --user enable --now bolt-serve.service bolt-strata-ui.service
```

关键点：

- `Environment=LD_LIBRARY_PATH=...`（层切分也要能加载 NCCL）；
- `MemorySwapMax=0`：宁可 OOM，也不要静默换页掉到 0.04 tok/s；
- `bolt-serve` 与 `bolt-serve-tp` 用 `Conflicts=` 互斥；
- `Restart=on-failure`，但 OOM 会反复重启——先修配置。

## 9. 停止与清理

```bash
# 前台：Ctrl-C

# 后台脚本：
bash scripts/run-draft.sh --stop      # 生产
bash scripts/run-tp.sh --stop         # 回退

# 手工：
pkill -f 'llama-server.*bolt74b'
sleep 3
nvidia-smi
```

如果显存没释放，说明进程还在退出中（保存 KV/释放 CUDA context），再等几秒。
仍然不释放就 `nvidia-smi --gpu-reset`（需要 root，且会杀掉该卡上所有进程）。

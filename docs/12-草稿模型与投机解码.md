# 12 · 草稿模型与投机解码

这一章回答三个问题：

1. 为什么加一个 **1.11 B 的小模型**，能让 74 B 的模型快 15%？
2. 为什么这个技巧在**层切分**下成立，在**张量并行**下反而失效？
3. 代价是什么，什么时候不该用？

---

## 1. 先复习：decode 为什么慢

生成第 N 个 token 时，模型要把**几乎所有权重**从显存读一遍，但每个权重只参与一次乘加。
这是典型的 **GEMV**（矩阵×向量），算术强度极低：

```
一步的时间 ≈ 要读的权重字节 ÷ 有效带宽
```

74 B 模型量化到 IQ2_XXS 后约 20.5 GiB。三张 3060 的有效带宽合计约 200 GB/s，
所以一步的理论下限是：

```
20.5 GiB ÷ 200 GB/s ≈ 0.1 秒 → 约 10 tok/s
```

实测 40–47 tok/s，是因为 MoE 每 token 只激活一部分专家（9B 而非 74B），
稠密部分才是每步必读的 4.6 GiB 左右。

关键点：**每生成 1 个 token，就要完整读一遍稠密权重。**
如果一次前向能"顺手"产出 4 个 token，这 4 个 token 就摊薄了同一次权重读取。

## 2. 投机解码：小模型起草，大模型一次验证

### 2.1 流程

假设当前已经生成了 `"今天天气"`：

```
第 1 步：草稿模型（1.11 B，很快）连续猜 4 个 token
         猜："真不错，适合出去走走"

第 2 步：目标模型（74 B）把这 4 个猜测和原文拼成一个批次，
         一次前向，同时算出每个位置"如果是我，会输出什么"

第 3 步：从第一个位置开始比对
         - 相同 → 接受，继续看下一个
         - 不同 → 拒绝，用目标模型自己的 token 替换，停止
```

如果 4 个全中，目标模型**一次前向产出 5 个 token**（4 个草稿 + 1 个额外验证位）；
如果第 1 个就错，只产出 1 个 token——退化成普通解码，只多花了草稿的时间。

### 2.2 为什么结果不会变差

验证不是"让大模型给小模型打分"，而是**用大模型自己的分布重新算一遍**：

- greedy（温度 0）下，被接受的 token 与大模型单独生成的 token **逐字节相同**；
- 采样模式下，拒绝/接受规则（rejection sampling）保证输出分布与不用草稿时一致。

所以投机解码是**无损加速**，不是"用小模型凑合"。

实测佐证：同一段代码提示，开/关草稿的输出**逐字节相同**；
自由写作类提示会出现极少数"接近并列"的 token 翻转，
这是验证批次从 1 变成 5 后浮点累加顺序不同造成的，属于正常数值差异。

### 2.3 加速比公式

```
加速比 ≈ (1 + 接受长度) / 1.2
```

- **接受长度**：平均每步被接受几个草稿 token。本机 1M + `n_max=4` 实测 **3.42**；
- **分母 1.2**：草稿自身的额外开销（起草一步约 11.6 ms，加上验证批次变宽）
  折算成约 20%，这是本机实测拟合出来的经验系数，不是理论常数。

代入：`(1 + 3.42) / 1.2 ≈ 3.7`。但验证批次从 1 变成 5 后，目标模型单步也变慢，
所以实际只有：层切分无草稿 **40.3 → 54–55**（+34%～+36%）；
相对 TP 回退的 46.6–47.7 约 **+15%**（1.17 倍）。都不是 3.7 倍。

> 这就是"第一性原理"在这里的作用：公式告诉你上限在哪，
> 实测告诉你验证批次的额外成本吃掉了多少。

## 3. 本项目用的草稿：NVIDIA DFlash

| 项 | 值 |
|---|---|
| 文件 | `dflash-NVIDIA-Nemotron-3.5-Bolt-74B-A9B-NVFP4.gguf` |
| 大小 | 998,242,560 字节（1.11 B 参数，NVFP4） |
| SHA256 | `080e1ea41c9562a7804dbf30c6fbd4d17e216c6b8ff666f88e6edb1816010194` |
| `block_size` | 8 |
| `target_layers` | `[2, 19, 36, 52, 69, 86]` |
| 官方接受长度（SPEED-Bench） | 4.30 |
| 本机实测（1M，`n_max=4`） | 3.42 |

`target_layers` 的意思是：草稿只在目标的这 6 层读取隐藏状态，
其余层的信息通过一个轻量的映射补上。这让草稿只有 1.11 B，
而不是"再跑一个 9 B 的模型"。

文档里有时叫它 **LiLiCorr 草稿**，指的是同一份文件；
上游仓库的名字是 `dflash-…-NVFP4.gguf`，本机另有一份改名为 `…-LiLiCorr.gguf`。

### 3.1 为什么不用通用的 Nano-4B 草稿

Nano-4B（2.18 GB）也能当草稿，走 llama.cpp 的 `draft-simple` 模式。
但它**不适合这个模型**：

- Bolt 是混合架构：40 个 Mamba/SSM 层 + 8 个注意力层；
- 验证被拒绝时，Mamba 状态必须回滚到"猜测之前"的快照；
- `draft-simple` 不会设置 `n_rs_seq`，回滚快照无效，状态会错。

DFlash 是按目标架构训练的，知道 `n_max+1` 个候选位置需要几份状态，
所以能正确回滚。

## 4. 为什么必须配层切分

这是本项目最容易踩的坑：**同一份草稿，配 TP 反而更慢，甚至 OOM**。

| 配置（1M） | decode | 结果 |
|---|---:|---|
| 层切分 + 草稿 | **54.0–55.0** | 生产 |
| TP + 草稿 @32K | 45.1 | 比层切分的 1M 还慢 |
| TP + 草稿 @1M | OOM | CUDA0 分配草稿 944 MB 失败 |

### 4.1 验证批次放大了 all-reduce

普通 decode 每步 1 个 token，TP 每层 all-reduce 的数据量很小。
开草稿后每步要验证 5 个位置，all-reduce 的数据量变成 5 倍。
TP 原本的通信成本（每 token 约 6 ms）被放大，正好吃掉草稿的收益。

层切分没有集合通信：第 1 张卡算完前几层，把激活传给第 2 张，依此类推。
验证 5 个位置只是让激活张量变宽，不产生额外的跨卡同步。

### 4.2 草稿本身在 TP 下更慢

| 后端 | 草稿一步 |
|---|---:|
| 层切分 | **11.6 ms** |
| TP（meta 后端） | **22.9 ms** |

草稿的最后一层要在**全词表**（十万级 token）上取 top-k 候选。
TP 把输出层切到三张卡，必须先把结果拼回来才能排序——又是一次通信。
层切分下输出层就在最后一张卡上，top-k 是本地操作。

### 4.3 显存

1M 上下文下，8 个注意力层的 KV 在 TP 下是**镜像**的（2 个 KV 头 < 3 张卡），
每卡约 2.25 GiB；层切分按层分布，平均每卡约 0.75 GiB。
省下来的 1.5 GiB，正好够放草稿（约 0.93 GiB）。

三件事叠加，结论很明确：

> **草稿与层切分是配套的。** 不是"多一种可选组合"，
> 而是"这两个优化只有绑在一起才成立"。

## 5. `n_max` 怎么选

`n_max` 是每步最多起草几个 token。

- 太小：摊薄不够，加速有限；
- 太大：验证批次变大，单步变慢；而且草稿越往后越不准，后几个位置大概率被拒。

本机扫描结果：

| 上下文 | KV | `n_max` | decode | 接受长度 |
|---:|---|---:|---:|---:|
| 1M | q4_0 | **4** | **54.0–55.0** | 3.42 |
| 1M | q4_0 | 3 | 48.5–50.6 | 2.70 |
| 200K | q8_0 | 3 | 55.5 | 2.92 |
| 400K | q8_0 | 3 | 55.2 | 2.92 |
| 32K（TP） | q8_0 | 4 | 45.1 | 2.83 |

怎么理解：

- **1M 用 4**：KV 已经很大，验证再宽一点就更接近显存上限；
- **200K/400K 用 3**：KV 小，3 个候选已经够摊薄，单步更轻；
- **代码/模板类任务**接受率更高，可以试 5；
- **自由创作**接受率低，`n_max=2–3` 可能更稳。

温度也会影响：温度 0.7 时接受长度下降，实测 49–52 tok/s。

自己扫一遍（同一段提示、同一 `max_tokens`）：

```bash
for n in 2 3 4 5; do
  NMAX=$n bash scripts/run-draft.sh --daemon
  # 记录 eval tok/s
  bash scripts/run-draft.sh --stop
done
```

## 6. 代价：预填充变慢

草稿不是免费的。为了保证验证时状态正确，草稿也要**把整个 prompt 过一遍**。
所以长 prompt 的 `prompt eval` 会明显变慢：

| 提示长度 | 回退（无草稿） | 生产（草稿） | 变化 |
|---:|---:|---:|---:|
| 19K | 1269 tok/s | 616 tok/s | 约 −51% |
| 200K | 约 940 tok/s（约 3.6 分钟） | 约 460 tok/s（413 秒） | 约 −51% |
| 1M | 约 17 分钟 | 30 分钟以上 | 约 −2 倍 |

注意：

- **短 prompt 不受影响**。草稿只处理"新来的那一段"和已缓存的上下文，
  日常对话仍然很快；
- **prefill 慢 ≠ 总时间慢**。如果你的任务是一次性读 200K 文档、只回答 50 个字，
  回退配置可能总时间更短；如果是长对话、持续生成，草稿的收益远大于代价。

判断方法：

```
总时间 ≈ prompt_tokens ÷ prefill_speed + output_tokens ÷ decode_speed
```

把两组数字代进去，哪个小用哪个。

## 7. 什么时候不该用草稿

| 场景 | 建议 |
|---|---|
| 超长 prompt、只回几个 token | `bash scripts/run-tp.sh`（回退） |
| 显存已经贴到 12 GB | 降 `-c` 到 200K，或回退 |
| 需要严格逐字节复现大模型输出 | greedy + 草稿也是逐字节一致的；但若对比不同批次，注意浮点差异 |
| 温度很高（>1.0） | 接受率低，收益可能为负；先测 |
| 草稿模型文件缺失 | `SPEC=none bash scripts/run-draft.sh` 可对照 |
| 显卡太少（1–2 张） | 先算显存：草稿要约 0.93 GiB |

## 8. 怎么开、怎么关

```bash
# 生产：开
bash scripts/run-draft.sh --daemon

# 同一套引擎，临时关草稿做对照
SPEC=none bash scripts/run-draft.sh --daemon

# 回退到 TP（完全不同的一套参数）
bash scripts/run-tp.sh --daemon
```

手工参数只有四行：

```
-md model/draft/dflash-...-NVFP4.gguf
-ngld all
--spec-type draft-dflash
--spec-draft-n-max 4 --spec-draft-n-min 0
```

少任何一行都可能"加载了草稿但没启用"，用
`grep -iE 'draft|accept' model/bolt-serve.log` 确认。

---

## 9. 一句话总结

> **decode 的瓶颈是"每个 token 读一遍权重"。草稿模型用很小的代价猜出后续几个 token，
> 让大模型一次前向验证多个位置，把权重读取摊薄。
> 它要求验证批次足够便宜——这正是层切分擅长、张量并行不擅长的事。
> 代价是预填充要过两遍 prompt，所以长 prompt、短回复的场景应回退到无草稿配置。**

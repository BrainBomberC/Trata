# 05 · 下载与校验

模型有 20+ GB，下载一次几小时。**下载策略和校验比下载速度更重要**——
下错一次，后面量化、启动、测速全部白做。

生产配置需要 **3 个文件**，全部来自同一个仓库：

| 2 | 草稿模型 `dflash-…-NVFP4.gguf` | ✅（不用草稿可跳过） | 998 MB |

## 2. 用脚本下载（推荐）

```bash
bash scripts/download-model.sh                  # 1) 主模型 → model/bolt74b/
PRESET=draft  bash scripts/download-model.sh    # 2) 草稿   → model/draft/
PRESET=mmproj bash scripts/download-model.sh    # 3) 投影器 → model/
```

它做的事：

1. 用 HTTP Range 请求取得远端真实大小；
2. 把文件切成 4 段并行下载（默认 `PARTS=4`）；
3. 每段独立按字节续传，中断后重跑即可；
4. 拼接后校验 SHA256；
5. 失败会保留分块，方便下次续传。

常用变体：

```bash
# 只取远端大小，不下载
bash scripts/download-model.sh --check
PRESET=draft bash scripts/download-model.sh --check

# 换并发
PARTS=8 bash scripts/download-model.sh

# 换源（显式变量优先于 PRESET）
REPO=unsloth/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-GGUF \
FILE=NVIDIA-Nemotron-3.5-Bolt-74B-A9B-IQ2_XXS.gguf \
PARTS=8 bash scripts/download-model.sh
```

### 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `PRESET` | `main` | `main` / `draft` / `mmproj`，会填好 REPO/FILE/DEST/EXPECT_SHA |
| `REPO` | `unsloth/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-GGUF` | ModelScope 仓库 |
| `FILE` | 随 PRESET | 文件名 |
| `DEST` | 随 PRESET | 主模型 `model/bolt74b`、草稿 `model/draft`、投影器 `model` |
| `PARTS` | `4` | 分块数 |
| `EXPECT_SHA` | 随 PRESET | 传空字符串可跳过；换 FILE 时自动置空 |
| `PROXY` | 空 | HF 兜底时使用的代理，如 `http://127.0.0.1:7897` |

## 3. 为什么不用 `curl -C -` 直接续传

一个真实踩坑：

> 下载中断后用 `curl --retry` 续传，分块大小全对、68 个采样点也全一致，
> 但整体 SHA 不符——最后只能整份重下。

原因：`curl --retry` 在 Range 请求失败重试时，可能从**该次请求的起点**重新下载并追加，
造成分块内部重复数据。文件大小看起来"差不多"，内容却错了。

本仓库的脚本改为 **bash 层续传**：

```bash
have=$(stat -c%s "$part")
curl -r $((start + have))-$end ... >> "$part"
```

每次都从"当前实际字节数"继续请求剩余范围，**绝不盲目重试追加**。
同时下载后检查 `have > total` 并截断。

## 4. 校验

```bash
sha256sum model/bolt74b/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-IQ2_XXS.gguf
```

和上面的 SHA 对比。22 GB 校验大约需要 1–2 分钟（取决于磁盘）。

也可以只用脚本校验：

```bash
bash scripts/verify-model.sh              # 主模型
bash scripts/verify-model.sh --draft      # 草稿
bash scripts/verify-model.sh --mmproj     # 投影器（顺带数张量）
bash scripts/verify-model.sh --all        # 三个都查
```

它会：

- 检查文件是否存在；
- 对比字节数（差 ≤64 字节只警告，见 §4.2）；
- 对比 SHA256；
- `--mmproj` 额外读 GGUF 头部数张量，不是 519 就直接判失败；
- 退出码 0 = 完整，3 = 缺失/不完整。

### 4.1 大小对但 SHA 不对

说明内容被破坏或续传拼接错了。**不要试图"修一修"**：

- 如果是分块下载，删掉 `.chunks-*` 和最终文件，重下；
- 如果只有某一段损坏，脚本的按字节续传可以只补那一段（但先删掉最终文件）。

### 4.2 SHA 和文档不一致

可能原因：

1. 托管方更新了文件（重新量化/重新上传）；
2. 你下的是另一个量化版本（文件名差一个 `UD-` / `AD-`）；
3. 元数据缓存。

本项目实测到过**只差 64 字节**的情况：两份文件的 843 个张量名、形状、
类型完全一致（`gen-expert-types.py` 输出逐行相同，tpfit 规则都是 240 条），
但 GGUF 元数据里某个字符串长度不同，导致整体 SHA 不同。这种差异不影响推理，
但会让 SHA 校验失败。视觉投影器也有同样现象（1,733,692,672 vs 1,733,692,736 字节）。

具体数字：

| 文件 | 托管元数据 | 本机实测 | 差异 |
|---|---|---|---|
| 主模型 | 22,018,326,464 B / `30c4eac4…108f` | 22,018,326,528 B / `91d63363…af75` | +64 B |
| 投影器 | 1,733,692,672 B / `acad0317…6f4f` | 1,733,692,736 B / `0ee891ea…26b0` | +64 B |

处理原则：

1. 先以 **ModelScope 元数据**的 SHA 为准；
2. 如果大小只差几十字节、张量清单一致（张量数、名字、形状、类型全对），可以继续用；
3. 如果差的是 MB/GB 级，或者张量数不对，**删掉重下**，不要试图修补。

下载脚本的 SHA 失败提示已经把这条写进去了，不会再让你误以为文件损坏。

## 5. 下载速度与耗时

本机实测（2026-10）：

| 源 | 速度 | 22 GB 耗时 |
|---|---:|---:|
| ModelScope 直连（单流） | 6.7–7.4 MB/s | 约 50–55 分钟 |
| ModelScope 4 路并行 | 约 11 MB/s | 约 33 分钟 |
| HF 走代理 | 0.1–1.2 MB/s | 5–60 小时 |
| hf-mirror.com | 约 0.34 MB/s | 约 18 小时 |

**注意代理**：如果机器设了全局 `http_proxy`，访问 ModelScope 可能被劫持或变慢。
脚本默认对 ModelScope 加 `--noproxy '*'` 直连。

## 6. 磁盘空间

下载过程中需要：

```
分块临时文件（等于文件大小） + 最终文件（等于文件大小） ≈ 2 × 22 GB = 44 GB
```

拼接完成后分块自动删除。如果磁盘只剩 25 GB，下载会失败。
先检查：

```bash
df -h model/
```

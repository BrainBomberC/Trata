# 01 · 第一性原理

这一章只回答一个问题：**生成一个 token，时间到底花在哪？**

看懂之后，你会自己推导出：

- 为什么 74B 模型能在 3 张 12 GB 卡上跑；
- 为什么速度卡在 46 tok/s，而不是 100；
- 为什么 43 GB 的模型比 22 GB 的模型慢 4 倍；
- 为什么"再量化狠一点"没有用。

---

## 1. 自回归解码：一次只算一个向量

大模型生成是串行的：第 `t` 个 token 依赖前 `t-1` 个。每一步，每一层做的事可以简化为：

```
y = W · x
```

- `W`：这一层的权重矩阵，可能有几亿个参数；
- `x`：当前 token 的激活向量（batch=1 时只有一行）。

### 1.1 它不是"算不动"，是"读不完"

矩阵乘法的运算量是 `2 × 行数 × 列数`，而要读的权重字节数是 `参数量 × 每参数字节`。
在 batch=1 时，**运算量/字节数**（算术强度）非常低：读一个 4 bit 权重，只做 2 次乘加。

GPU 的算力早就过剩了，瓶颈是把权重从显存搬到计算单元：

```
每 token 时间 ≈ 必须读取的权重字节数 ÷ 有效显存带宽
```

### 1.2 用实测校准"有效带宽"

RTX 3060 标称显存带宽 **360 GB/s**。但 batch=1 的 GEMV 内核读不满：

- 层切分实测：每 token 读 **4.88 GiB**，速度 **40.27 tok/s**
- 反推：`4.88 GiB × 40.27 / s ≈ 197 GB/s`（标称的 55%）
- 张量并行时矩阵被切窄，单卡有效带宽进一步降到约 **114 GB/s**

**记住这个 197 GB/s**，后面所有估算都用它。它不是理论值，是这台机器的现实值。

> 为什么只有 55%？GEMV 的访存模式、kernel 启动开销、以及每层之间的同步都会吃掉带宽。
> 这也解释了为什么"kernel 融合"之类的微优化收益很小：瓶颈在 DRAM，不在指令。

## 2. MoE：74B 参数，每 token 只读 4.88 GiB

### 2.1 稠密 vs 稀疏

普通 Transformer 的 FFN 是稠密的：每个 token 都要过全部 FFN 权重。
MoE（Mixture of Experts）把 FFN 拆成很多个"专家"，每个 token 只选其中 top-k 个：

```
74B 总参数 = 稠密部分（每 token 必读）+ 专家部分（每 token 只读 top-9）
```

Bolt 74B 的配置：

| 项 | 数值 |
|---|---:|
| 总参数 | 74B |
| 每 token 激活 | 9B |
| 层数 | 88 |
| MoE 层 | 40（每层 240–496 个专家，top-9） |
| SSM/Mamba2 层 | 40 |
| 全注意力层 | 8 |

### 2.2 每 token 的字节账单（IQ2_XXS，约 2.38 bpw）

| 组成 | 每 token 字节 |
|---|---:|
| `ssm_in` 输入投影（40 层） | 1.22 GiB |
| `ssm_out` 输出投影（40 层） | 0.54 GiB |
| LM head + token embedding | 0.41 GiB |
| 共享专家 + latent + 注意力 | 1.11 GiB |
| 被选中的 9 个专家 × 40 层 | ≈0.36 GiB |
| **合计** | **≈4.88 GiB** |

关键洞察：**专家部分只占 0.36 GiB**。即使总参数 74B，每 token 真正流动的只有 4.88 GiB。
这就是"消费级显卡跑 74B"的数学基础。

### 2.3 反例：为什么 120B 不行

120B 模型的专家集合是 **46.4 GiB**，而本机可用内存约 42 GiB：

```
46.4 GiB > 42 GiB  →  必然缺页  →  每 token 从 USB2 盘补页
理论速度 ≈ 0.05 tok/s，实测 0.04 tok/s
```

这不是"再调调"的问题，是算术上不成立。**先算，能省掉十几个小时的下载和量化。**

## 3. 三级存储：显存、内存、磁盘

| 位置 | 本机实测带宽 | 22 GB 权重每 token 耗时 | 对应 tok/s |
|---|---:|---:|---:|
| 显存（三卡合计 34.4 GiB） | 197 GB/s | 25 ms | ~40 |
| 内存（DDR4，46.9 GiB） | 44.7 GB/s | 113 ms | ~8.8 |
| USB2 硬盘 | 43.8 MB/s | 8 分钟 | ~0.002 |

### 3.1 最重要的一条判据

> **模型文件必须比物理内存小 6–8 GiB。**

为什么是 6–8 GiB，而不是"等于内存"？

- 操作系统、网页服务、CUDA 上下文、页缓存本身都要占内存；
- mmap 的模型页是**可回收的**（`Cached`），内核在内存紧张时会优先驱逐它们；
- 一旦被驱逐，下一次读这个权重就要从磁盘补——而磁盘比内存慢 **1000 倍**。

### 3.2 实测证据

| 模型文件 | 大小 | 与 46.9 GiB 内存的关系 | 实测 |
|---|---:|---|---:|
| IQ2_XXS | 20.5 GiB | 余量 26 GiB | **40.27 tok/s** |
| IQ4_XS | 43.4 GiB | 余量 3.5 GiB | **11–14 tok/s**（sda 持续读 27–30 MB/s，正在掉盘） |
| 120B UD-IQ3_XXS | 57.3 GiB | 超出内存 10 GiB | **0.04 tok/s** |

### 3.3 一个记账陷阱

`free` 显示的 `used` 只有 4–7 GiB，不代表内存够用。
mmap 的模型页记在 `Cached` 里。要看：

```bash
free -h          # 看 MemFree 和 Cached
cat /proc/meminfo | grep -E 'MemFree|Cached|MemAvailable'
```

如果 `MemFree` 只剩几百 MB、`Cached` 有 40 GiB，说明页缓存已经顶到天花板了。

## 4. KV 缓存：长上下文的隐藏成本

### 4.1 为什么需要 KV 缓存

生成第 `t` 个 token 时，注意力要回看前面所有 token 的 Key/Value。
如果每步都重算，复杂度是 `O(t²)`。KV 缓存把历史的 K/V 存下来，每步只算新的一个。

代价：**上下文越长，KV 缓存越大**。

### 4.2 公式

```
KV 字节 = 2（K 和 V）
        × 注意力层数
        × KV 头数
        × head_dim
        × 上下文长度
        × 每元素字节数
```

本模型（`head_dim = 4096 / 32 = 128`，注意力层 8，KV 头 2）：

| 上下文 | KV 类型 | 每份大小 | 说明 |
|---:|---|---:|---|
| 200K | q8_0（约 1.06 B/元素） | **约 850 MiB** | 层切分，每卡各存自己那段 |
| 1M | q4_0（约 0.56 B/元素） | **约 2.25 GiB** | 张量并行时 3 卡**各镜像一份**；层切分平均每卡约 0.75 GiB |

### 4.3 为什么 1M + TP 特别贵（所以生产改用层切分）

注意力层只有 **2 个 KV 头**（32 个 Q 头，GQA 16:1）。
张量并行要求"每张卡至少分到 1 个 KV 头"，2 个头分不到 3 张卡上，
于是 llama.cpp 只能把 KV 缓存**在每张卡上完整镜像一份**。

```
每卡预算 = 权重 7.5 GB + 镜像 KV 2.3 GiB + 计算缓冲 1.2 GiB ≈ 11 GB
```

12 GB 的卡只剩约 1 GB 余量。原版 IQ2（22.0 GB）在 `-ub 128` 下差约 1 GiB 装不下，
所以有了 19.58 GiB 的 `-tpfit`；把 `-ub` 降到 64 也能装下，所以 tpfit 现在是可选项。

更重要的结论是**层切分把镜像 KV 消掉了**：1M 下每卡只要约 0.75 GiB，
比 TP 的 2.25 GiB 省 1.5 GiB —— 这正好够放 0.93 GiB 的草稿模型。
生产配置的显存账就是这么成立的。

## 5. 多卡：流水线 vs 真并行

### 5.1 层切分（`-sm layer`）

```
token → [卡0: 第 0–29 层] → [卡1: 第 30–58 层] → [卡2: 第 59–87 层] → 输出
```

- 同一时刻只有一张卡在工作；
- 有效带宽 = 单卡带宽；
- 三卡利用率约 28%/32%/26%，加起来 ~100%——**机器在排队，不是在并行**；
- 优点：零通信开销，预填充最快（实测 1489 tok/s）。

### 5.2 张量并行（`-sm tensor -ts 1,1,1`）

```
每层权重切成 3 份 → 三张卡同时算 → all-reduce 求和 → 下一层
```

- 有效带宽 ≈ 三卡之和；
- 每层一次跨卡归约，88 层约 **80 次 all-reduce/token**；
- 每次 55–87 µs（NCCL ring，PCIe Gen3 x8/x4/x8），合计 **4.4–6.0 ms/token**；
- 预填充反而变慢：矩阵被切窄，GEMM 效率下降（1489 → 940 tok/s，-37%）。

### 5.3 什么时候值得用张量并行

| 场景 | 选择 | 原因 |
|---|---|---|
| 单流聊天，显卡 ≥3，**有 DFlash 草稿** | **层切分 + 草稿（生产）** | 54–55 tok/s；TP 下验证批次放大通信，只有 45.1 |
| 单流聊天，显卡 ≥3，**无草稿** | 张量并行 | 多卡带宽叠加，decode 46.6–47.7 |
| 一次读 200K 冷提示 | **回退到 TP 无草稿** | 草稿要跟着读 prompt，预填充慢约一倍 |
| 2 张卡 | 张量并行收益有限 | 实测 45.4 vs 层切分 40.3，只快 13% |
| 模型单卡装得下 | 不切 | 通信是纯开销 |

### 5.4 为什么速度停在 46，而不是 3 × 40 = 120

Amdahl 定律的直观版：把工作分给 3 张卡，但每层结束都要等最慢的卡，并且加一次通信。

实测 kernel 时间：

| 类别 | 占比 | 换算到 21.6 ms/token |
|---|---:|---:|
| matmul / GEMV（读权重） | 52.7% | ≈11.4 ms |
| **NCCL all-reduce** | **27.6%** | ≈6.0 ms |
| elementwise（norm/quantize/copy） | 14.3% | ≈3.1 ms |
| SSM scan / conv | 3.3% | ≈0.7 ms |

三块墙：

1. **带宽墙**：11.4 ms 是每卡约 1.3 GB ÷ 114 GB/s；
2. **通信墙**：80 次 all-reduce，每次几十微秒；
3. **固定开销墙**：1800 多个小 kernel，每个约 2.7 µs。

**降量化精度只能动第一块墙**。当第一块墙从 25 ms 降到 11 ms 后，另外两块就成了主导——
这就是"再量化 18% 速度完全不变"的原因。

### 5.5 投机解码：换一个维度绕过这三堵墙

上面三堵墙都在回答"怎么让一步更快"。投机解码换了个问题：
**能不能让一步多出几个 token？**

一个 1.11 B 的草稿模型先猜 4 个 token，主模型一次前向同时验证这 4 个位置。
如果全中，一次权重读取产出 5 个 token；第一个就错，最多退化成普通解码。

```
加速比 ≈ (1 + 接受长度) / 1.2
```

本机 `n_max=4`、接受长度 3.42 → 实测 40.3（层切分无草稿）→ **54–55 tok/s**。
注意它**没有让任何一步变快**，只是把权重读取摊到了更多 token 上，所以能和量化叠加。

它也有自己的墙：

- **验证批次变宽**：TP 的 all-reduce 数据量随候选数放大，收益被通信吃掉（TP + 草稿 @32K 只有 45.1）；
- **草稿也要读 prompt**：长 prompt 的预填充约慢一倍；
- **草稿要放得下**：0.93 GiB，只有层切分省出的镜像 KV 才腾得出这块空间。

完整推导 → [12-草稿模型与投机解码](12-草稿模型与投机解码.md)。

## 6. 预填充 vs 解码：两种完全不同的负载

| 阶段 | 在做什么 | 瓶颈 | 本机实测 |
|---|---|---|---:|
| **prefill（预填充）** | 一次性读入整段提示，矩阵乘矩阵 | **算力** | 706–1489 tok/s |
| **decode（解码）** | 逐 token 生成，矩阵乘向量 | **显存带宽 + 通信** | 54–55 tok/s（生产） / 46.6–47.7（回退） |

这解释了两个常见困惑：

- "为什么 200K 提示要等 2 分钟？"——预填充要处理 20 万 token 的注意力，是算力密集型；
- "为什么首 token 之后反而快了？"——进入 decode 后每步只算一个 token，负载性质变了。

FlashAttention（`-fa on`）主要优化预填充和长上下文注意力，**长上下文必须开**。

## 7. 量化：用精度换字节

### 7.1 bpw 是什么

`bpw = bits per weight`，平均每个权重占多少 bit。

| 类型 | bpw（约） | 22 GB 模型缩到 | 质量 |
|---|---:|---:|---|
| BF16 | 16 | 148 GB | 基准 |
| Q8_0 | 8.5 | 75 GB | 几乎无损 |
| Q6_K | 6.6 | 58 GB | 很接近无损 |
| Q4_K_M | 4.8 | 42 GB | 日常可用 |
| IQ3_XXS | 3.1 | 28 GB | 有可见损失 |
| **IQ2_XXS** | **2.38** | **22 GB** | **能用，但不无损** |
| IQ1_M | 1.8 | 17 GB | 明显退化 |

### 7.2 本项目的选择逻辑

1. 内存上限 46.9 − 6~8 = **约 39–41 GiB**；
2. 三卡显存 34.4 GiB，模型最好能全进显存；
3. 在"文件 ≤ 34 GiB 且质量可接受"的量化里，**IQ2_XXS（20.5 GiB）**是唯一稳妥选择；
4. IQ3_XXS（33.85 GiB）理论上能装进内存，但加上 KV 和缓冲后 TP 装不下，且下载/量化时间翻倍。

### 7.3 量化救不了什么

- 救不了**通信墙**：权重再小，all-reduce 次数不变；
- 救不了**固定开销**：小 kernel 数量不变；
- 救不了**内存不足**：如果模型仍大于内存，照样掉盘；
- 救不了**质量**：2 bit 的 PPL 5.76，和 BF16 不是一个水平。

## 8. 把公式用起来：一分钟估算

给定你的机器，按下面顺序算：

```text
1. 模型文件上限 = 物理内存 − 6~8 GiB
2. 每卡权重   = 模型文件 / 卡数
3. 每卡 KV    = 见第 4 节公式（注意镜像）
4. 每卡缓冲   ≈ 1–3 GiB（随 -ub 和上下文增长）
5. 若 2+3+4 > 单卡显存 → 降量化 / 减上下文 / 减 -ub / 换层切分
6. 预期 tok/s ≈ 单卡有效带宽 × 卡数 ÷ 每 token 字节数（再乘 0.7 的通信折扣）
```

本机代入：

```text
1. 46.9 − 7 = 39.9 GiB          → 22 GB 模型安全
2. 20.5 GiB / 3 ≈ 6.8 GiB
3. 2.25 GiB（1M q4_0，镜像）
4. ≈1.2 GiB
5. 6.8 + 2.25 + 1.2 ≈ 10.3 GiB < 12 GiB  ✅
6. 197 × 3 / 4.88 × 0.7 ≈ 85 tok/s（乐观上限）；实测 46，差距就是通信与固定开销
```

第 6 步的"乐观上限"永远达不到——它的价值是告诉你**离理论还有多远**，
以及**继续优化哪一块最划算**。

## 9. 本章小结

| 结论 | 用途 |
|---|---|
| decode 时间 ≈ 字节 ÷ 带宽 | 预测速度、判断该不该升级硬件 |
| MoE 每 token 只读 top-k 专家 | 解释 74B 为何能跑 |
| 模型 ≤ 内存 − 6~8 GiB | 决定量化档位与生死 |
| KV 随上下文线性增长 | 决定 1M 能不能开、要不要镜像 |
| 层切分 = 流水线，TP = 真并行 | 决定 `-sm` 参数 |
| 量化只动带宽墙 | 避免在错误的墙上优化 |

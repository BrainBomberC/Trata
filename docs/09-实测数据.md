# 09 · 实测数据

这一章是所有结论的来源。数字都来自本机（3 × RTX 3060 12 GB + 46.9 GiB DDR4），
测量日志在 `benchmarks/logs/`。

**先说口径**，否则数字没法比较：

- 单流（`-np 1`），greedy 解码（除非另注温度）；
- `-fa on`；
- 200K/400K 配置用 `-ctk/-ctv q8_0`，1M 配置用 q4_0；
- `-t 17`；
- decode 取稳定生成段的平均，不含首 token；
- prefill 是 200K 冷提示的读数（除非另注）；
- "接受长度"= 每个验证步平均被接受的草稿 token 数。

### 1.3 几个直接结论

1. **草稿把 1M 下的 47 提升到 54–55**：接受长度 3.42，等效每步验证约 4.4 个 token，
   摊薄了每 token 的权重读取（公式见 [12](12-草稿模型与投机解码.md)）。
2. **草稿必须配层切分**。同一套 1M + 草稿，TP 只有 45.1（32K）/ 1M 直接 OOM；
   原因见 §3.2。
3. **`n_max` 要按上下文扫**：1M 用 4，200K/400K 用 3 更快。
4. **草稿的代价是预填充**：19K prompt 1269 → 616 tok/s；1M 要 30 分钟以上。
5. **回退配置仍有一席之地**：TP 46.6–47.7 的预填充是生产配置的约 2 倍快，
   适合"超长 prompt、只回几个字"。
6. **120B 的 0.04 tok/s 不是调参问题**，是内存算术上不可能（见 02）。

## 2. 显存分布

### 2.1 200K / 层切分 / IQ2

| 项 | 数值 |
|---|---:|
| 权重分布（三卡） | 5.53 / 7.43 / 7.49 GiB + CPU 映射 0.54 GiB |
| 200K KV（q8_0，总量，按层分布到三卡） | 850 MiB（平均约 283 MiB/卡） |
| SSM 状态 | 164.68 MiB |
| compute buffer | 3.2 GiB（`-ub 256` 时） |

### 2.2 1M / TP / tpfit

| 项 | 每卡 |
|---|---:|
| 权重 | ≈ 6.84 GiB（19.58 GiB ÷ 3，含镜像/对齐开销后略高） |
| KV（q4_0，镜像） | ≈ 2.25 GiB |
| compute buffer（`-ub 128`） | ≈ 1.2 GiB |
| 运行时 | ≈ 0.3 GiB |
| **实测 `nvidia-smi`** | **11.1 / 11.3 / 11.8 GB** |

`-ub 256` 在 1M 下会 OOM：device 2 申请 1292 MiB 失败。
`-ub 64` 可再省约 0.3 GiB，速度基本不变。

### 2.3 1M / 层切分 + 草稿（生产）

层切分下 KV **不需要镜像**：8 个注意力层分散到三张卡，1M 的 q4_0 KV
总量约 2.25 GiB，平均每卡约 0.75 GiB。这正是生产配置能再塞下草稿的原因：

| 项 | 层切分 + 草稿 | TP + 草稿 |
|---|---|---|
| KV（1M，q4_0） | 约 0.75 GiB/卡（按层分布） | 约 2.25 GiB/卡（镜像） |
| 草稿 | 约 0.93 GiB，整份 | 同左 |
| 结果 | 装得下，54–55 tok/s | CUDA0 分配 944 MB 失败 |

## 3. 张量并行的成本拆解

`nsys --cuda-graph-trace=node`，每 token 每卡：

| 类别 | 占比 | 调用/token/卡 | 平均每次 |
|---|---:|---:|---:|
| matmul / GEMV（读权重） | **52.7%** | 538 | 33.9 µs |
| **NCCL all-reduce** | **27.6%** | 81–110 | 86.8 µs |
| elementwise（norm/broadcast/quantize/cpy） | 14.3% | 1831 | 2.7 µs |
| SSM scan / conv | 3.3% | 165 | 6.8 µs |

换算到实测 21.6 ms/token：

```
matmul        ≈ 11.4 ms
NCCL          ≈  6.0 ms
elementwise   ≈  3.1 ms
SSM           ≈  0.7 ms
```

单卡 kernel 时间：**0.282 / 0.292 / 0.257 s**。
第三张卡少干 12%，每次屏障另外两张都要等它——这是 `-ts 1,1,1` 下的真实不均衡。

### 3.1 三堵墙

1. **带宽墙**：11.4 ms 是每卡约 1.3 GB 权重 ÷ 约 114 GB/s。
   切分后矩阵变窄，GEMV 效率从层切分的 211 GB/s 掉到 114 GB/s。
2. **通信墙**：80 次 all-reduce/token，每次 55–87 µs，合计 4.4–6.0 ms。
3. **固定开销**：1800 多个小 kernel，每个约 2.7 µs。

**降量化精度救不了 TP 的速度**：实测每 token 少读 18% 的 tpfit 与原版 IQ2
在 TP 下都是 46.1–46.4 tok/s——已经撞在通信/开销墙上。
量化只在**装不下**的时候有意义。

### 3.2 为什么"TP + 草稿"反而输给"层切分 + 草稿"

| 配置（1M） | decode | 说明 |
|---|---:|---|
| 层切分 + 草稿 | **54.0–55.0** | 生产 |
| TP + 草稿（32K） | 45.1 | 32K 已经比生产的 1M 慢 |
| TP + 草稿（1M） | OOM | CUDA0 分配草稿的 944 MB 失败 |

三个独立原因：

1. **验证批次让 all-reduce 更贵**。草稿每步提交 `n_max+1=5` 个 token，
   TP 的每次 all-reduce 数据量随之变大，通信时间不再是单 token 时的 6 ms；
   层切分没有集合通信，验证批次几乎是免费的。
2. **草稿本身在 TP 下更慢**。meta 后端里草稿的一步是 **22.9 ms**，
   层切分只要 **11.6 ms**——草稿的 head 要在全词表上做 top-k，
   TP 需要把切分后的输出拼回来，正好打在通信墙上。
3. **显存**。1M + TP 时每卡 KV 已经镜像到约 2.25 GiB，再塞 944 MB 的草稿，
   CUDA0 直接分配失败。

所以本项目的结论是：**草稿与层切分是配套的**。这不是"多一种选择"，
而是"这两个优化只有绑在一起才成立"。

## 4. 负结果：试过、无效，别重复

| 手段 | 实测结果 |
|---|---|
| 跳过 608 个 ADD / 289 个 MUL / 160 个 SCALE | 45.78 → 46.6 / 46.04 / 45.97，全在噪声内；跳过 ADD 后输出变乱码，但速度不变 |
| 整 token 单 CUDA graph 捕获（4601 节点，含 NCCL） | 44.0（开归约）/ 56.1（关归约），比不捕获**慢 4%** |
| `NCCL_PROTO=LL128` | 45.3（默认 46.1） |
| `NCCL_ALGO=Tree` | 43.2 |
| `NCCL_ALGO=Tree + Simple` | 42.7 |
| 不用 NCCL，走蝴蝶归约 | 36.4 |
| `NCCL_P2P_DISABLE=1` | 45.9（无变化） |
| 4 槽并发（层切分） | 33.2 聚合（比单流还低） |
| 降量化（每 token −18%）后跑 TP | 46.37 → 46.1（完全没变） |
| ngram 投机解码 | 40.27 → 38.7 / 39.2 / 35.7（无收益，无 MTP head） |
| TP×3 + DFlash 草稿 @32K | 45.1（层切分 1M 是 54–55；草稿在 meta 后端一步 22.9 ms vs 11.6 ms） |
| TP×3 + DFlash 草稿 @1M | OOM（CUDA0 分配草稿 944 MB 失败） |
| DFlash 草稿放 CPU（`-ngld 0`） | 21.9（草稿每步要走 PCIe/RAM，抵消全部收益） |
| 1M + 草稿改 `n_max=3` | 48.5–50.6（比 4 慢；接受长度 2.70 vs 3.42） |
| Nano-4B 通用草稿（`draft-simple`） | 未采用：该模式不设 `n_rs_seq`，Mamba 回滚快照不成立 |

这些负结果的价值：**它们把"还能怎么优化"的空间封死了**。
如果你想到类似点子，先看这张表，别重复花时间。

### 4.1 为什么 CUDA graph 反而更慢

整 token 捕获把 4601 个节点合成一张图，减少了 launch 开销，
但也：

- 让 NCCL 的通信无法与计算重叠（图内是严格串行）；
- 增加了图重放的管理开销；
- 本机瓶颈是带宽 + 屏障，不是 kernel launch。

所以"减少 launch"没有命中真正的瓶颈。

## 5. 硬件实测上限

| 项 | 实测 |
|---|---:|
| 三卡可用显存合计 | 34.42 GiB |
| PCIe | Gen3 x8 / x4 / x8；H2D 5.98 / 3.12 / 5.98 GB/s |
| 单卡 decode 有效带宽 | **≈197–211 GB/s**（标称 360，GEMV 现实效率 55–59%） |
| 主机内存顺序读 | 44.68 GB/s |
| 模型盘 | USB2，**43.8 MB/s** |
| 22 GB 模型加载时间 | 约 8 分钟（USB2） |

### 5.1 带宽为什么只有标称的 55%

batch=1 的 decode 是 GEMV：每个权重只参与一次乘加，算术强度极低。
此时性能由**内存延迟 + 有效并发**决定，不是纯带宽。
3060 的 360 GB/s 是理论峰值，实测 197 GB/s 已经是很好的 GEMV 效率。

这也是为什么**层切分能到 211 GB/s、TP 只有 114 GB/s**：
TP 把矩阵切窄后，每张卡同时能发起的有效内存请求变少。

## 7. 如何自己复测

### 7.1 decode / prefill

用 `llama-bench`（同一份编译产物）：

```bash
./llama.cpp/build-nccl/bin/llama-bench \
  -m model/bolt74b/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-IQ2_XXS-tpfit.gguf \
  -ngl 99 -sm tensor -ts 1,1,1 -fa 1 \
  -ctk q4_0 -ctv q4_0 \
  -p 512 -n 128 -r 3
```

注意 `llama-bench` 不会自动设 `LLAMA_SM_TENSOR_ALLOW_ARCH`，需要先 `export`。

### 7.2 草稿接受长度

`llama-server` 的每次响应 `timings` 里有投机解码字段。跑一段固定长度的生成，
看日志或 `/metrics` 里的 `draft acceptance` / `mean acc len`：

```bash
bash scripts/run-draft.sh --daemon
curl -s --noproxy '*' http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"bolt74b","messages":[{"role":"user","content":"用 300 字介绍 SSD"}],"max_tokens":300}' \
  | python3 -m json.tool
```

扫 `n_max`：

```bash
for n in 2 3 4 5 6; do
  NMAX=$n bash scripts/run-draft.sh --daemon
  # 跑同一段提示，记录 eval tok/s 与 mean acc len
  bash scripts/run-draft.sh --stop
done
```

同一段提示、固定 `max_tokens`，结果才有可比性。温度 0 与 0.7 的接受率不同，
不要混着比。

### 7.3 PPL

```bash
./llama.cpp/build-nccl/bin/llama-perplexity \
  -m model/bolt74b/...-IQ2_XXS.gguf \
  -f wiki.test.raw -c 4096 --chunks 32
```

需要自备 `wiki.test.raw`（wikitext-2 测试集，UTF-8 纯文本）。

### 7.4 长上下文 prefill

```bash
# 生成 200K token 的提示，测 prefill 时间
python3 - <<'PY' > /tmp/long.txt
print("The quick brown fox jumps over the lazy dog. " * 30000)
PY

curl -s http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d "$(python3 -c '
import json
text=open("/tmp/long.txt").read()
print(json.dumps({"model":"bolt74b","messages":[{"role":"user","content":text}],"max_tokens":1}))')" \
  | python3 -m json.tool
```

看返回里的 `timings.prompt_ms` / `prompt_per_second`。

### 7.5 显存

```bash
nvidia-smi --query-gpu=index,memory.used,memory.total,utilization.gpu \
  --format=csv -l 1
```

## 8. 数据的可信度

- **decode / prefill / 接受长度**：来自 llama-server 自己的 `timings`，不是客户端计时，可信；
- **PPL**：`llama-perplexity` 标准输出，可复现；
- **profiler 占比**：nsys 会放大绝对时间，但**比例**可信；
- **tpfit PPL**：未测，文档里明确标注"未测"，不拿经验值冒充实测。
